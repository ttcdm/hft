# Devnet end-to-end harness (R2)

Run: `npm run devnet:e2e` (from a machine that can reach https://api.devnet.solana.com).
Optional env:
- `DEVNET_RPC_URL`: the devnet RPC to use (must not look like mainnet). **A private devnet endpoint is recommended**: the public `api.devnet.solana.com` rate-limits (429) the holder lookups the eligibility check needs, and the run then stops with the holder shares unknown. Set it in your shell for the run; the harness never prints it (the devnet guard logs scheme and host only, and error text is scrubbed of URLs), and never reads `.env`.
- `RPC_MAX_REQUESTS_PER_SEC`: the trading Connection's client-side request cap (docs/ENV.md). Against the public `api.devnet.solana.com` the harness sets 10 unless you set it (its limit is about 15 a second; a sell it refuses is resent after 0.5, 1 and 2 s, then watched, with resends, until it lands or its blockhash expires; only an expired, unseen one fails `RPC_RATE_LIMITED`, with no pending sell). Not set for a private `DEVNET_RPC_URL`.
- `DEVNET_MINTS=<comma list of active pump.fun devnet mints>`: tried first.
- `DEVNET_NO_WAIVER=1`: forbid the holder-limit waiver described below.
- `DEVNET_CLUSTER_CHECK=1`: run step (i) below. Unset, (i) is skipped with an INFO line. The throwaway wallet needs about 0.4 SOL free.
- `DEVNET_DUMP_SOL=<sol>`: run step (h) below, with at most that much SOL for the seed. The seed is sized from the new coin's own curve (see (h)); the step refuses, with the figure, when the curve needs more. Unset, (h) is skipped with an INFO line. The throwaway wallet needs the seed plus the app's buy plus 0.3 SOL.
- `DEVNET_RELEASE_GATES=1`: run step (k) below (SHADOW then PAPER over two launches each). Unset, (k) is skipped with an INFO line. The throwaway wallet needs about 1.2 SOL free.
- `DEVNET_FEED_SWITCH=1`: run step (t) below (two quick RPC switches, B7/B10). Unset, (t) is skipped with an INFO line. The throwaway wallet needs 0.1 SOL free (the step refuses to start below that, with the figures); it lends 0.05 SOL to one throwaway creator and spends about 0.02 (one coin's rent and fees; 0.005 on the local validator).
- `DEVNET_FEED_WATCHDOG=1`: run step (w) below (a subscription on a deaf socket is noticed and moved, devnet run 25). Unset, (w) is skipped with an INFO line. The throwaway wallet needs 0.1 SOL free (the step refuses to start below that, with the figures); it lends 0.05 SOL to one throwaway creator and spends about 0.012 (two coins' rent and fees). About 1 minute.
- `DEVNET_SELLER_NEVER_BOUGHT=1`: run step (u) below (a seller that never bought, B3). Unset, (u) is skipped with an INFO line. The throwaway wallet needs 0.15 SOL free (refused below that, with the figures); it lends about 0.11 SOL to three throwaway wallets and spends about 0.03 (one coin, two token accounts, curve fees; 0.012 on the local validator).
- `DEVNET_LOSS_FLOOR=1`: run step (n) below (the net daily PnL floor and its latch, task 3C). Unset, (n) is skipped with an INFO line. The throwaway wallet needs 0.05 SOL free (refused below that); one buy and full sell of the harness mint, about 0.003 SOL of fees (0.0016 on the local validator). No temp wallet.
- `DEVNET_READINESS_GATE=1`: run step (l) below (every LIVE buy re-checks live readiness, task 3A). Unset, (l) is skipped with an INFO line. The throwaway wallet needs 0.05 SOL free (refused below that); one buy and full sell of the harness mint, about 0.003 SOL of fees. No temp wallet, no key file: the planted row's mint and signature are made-up strings that never receive anything.
- `DEVNET_SESSION_SPEND=1`: run step (m) below (a 5-buy DEVNET_LIVE auto session, its spentSol against the wallet, task 3B). Unset, (m) is skipped with an INFO line. The throwaway wallet needs 0.3 SOL free (refused below that, with the figures); it lends 0.15 SOL to one throwaway coin creator (refunded) and spends about 0.04 (five coins' rent, five round trips' fees and curve fees; 0.030 on the local validator).
- `DEVNET_KILL_RESTART=1`: run step (o) below (the auto kill and the kill switch survive a restart, task 3E). Unset, (o) is skipped with an INFO line. The throwaway wallet needs 0.25 SOL free (refused below that); it lends 0.15 SOL to the step's own server wallet and 0.03 to a coin creator (both refunded) and spends about 0.01 (one coin, one round trip; 0.008 on the local validator). It boots `server.ts` four times, about 2 minutes.
- `DEVNET_REENTRY_BLOCK=1`: run step (p) below (no re-entry into a mint after an exit, task 3F). Unset, (p) is skipped with an INFO line. The throwaway wallet needs 0.05 SOL free (refused below that); it lends 0.012 SOL to a coin creator (refunded at once) and spends about 0.01 (one coin's rent and one round trip; 0.008 on the local validator).
- `DEVNET_CURVE_CAP=1` (with `DEVNET_RELEASE_GATES=1`): add the curve-cap push to (k). **Large SOL, off by default**: about 25.8 SOL with 30 SOL virtual reserves, so the throwaway wallet needs about 27 SOL free (the step computes the figure from the new coin's own curve and refuses to start below it plus 1 SOL); about 0.7 SOL is lost to curve fees.

## Safety
- Devnet only. The preload `scripts/devnet_guard.cjs` wraps fetch and http/https request/get, logs every attempt to stderr
  and throws on anything matching /mainnet|jito\.wtf/i.
- The harness sets its own environment and never reads `.env`: `SOLANA_RPC_URL` devnet, no `JITO_BLOCK_ENGINE_URL`
  (as on devnet normally, so the RPC transport sends; a dead Jito URL makes readiness report Jito OFFLINE and arming refuses), `ENABLE_RPC_FALLBACK=true`, `JITO_MAX_RETRIES=1`, `JITO_RETRY_INTERVAL_MS=200`,
  `APEX_DB_PATH` and `SIGNER_KEYPAIR_PATH` in a fresh temp directory, `ALLOW_LIVE_REAL_MONEY_TRADING=false`.
- It aborts unless `getGenesisHash()` equals the devnet hash `EtWTRABZaYq6iMfeYKouRu166VU2xqa1wcaWoxPkrZBG`. Only then does it switch the
  real-money environment variable on, inside its own process (it is never set in your shell or in any file).
- The keypair is a throwaway generated in the temp directory. The repo keypair is never used. If the address cannot be
  funded the harness prints the address, runs only the simulate stage, and exits 1 (UNFUNDED).
- Every throwaway wallet steps (i), (k), (t) and (u) create (creators, buyers, the curve-cap pusher) is written to `<scratch>/temp-wallets/<pubkey>.json` (mode 600, never overwritten) before any SOL is sent to it, and the harness never deletes it. If a refund fails, `solana transfer --keypair <scratch>/temp-wallets/<pubkey>.json <throwaway> ALL --url devnet` gets the SOL back.
- Faucet: no airdrop by default and never a retry loop. `DEVNET_AIRDROP_ONCE=1` sends exactly one request for an empty wallet.
  Trade size scales to the balance (about 8% of it, max 0.01 SOL, because of the 10% spendable ceiling); below 0.03 SOL it does not try to trade. 0.03 SOL is not enough to trade, though: the 10% ceiling needs about 0.075 SOL, and a fresh wallet about 0.1 SOL, because the 20% round-trip check counts the first buy's token-account rent (R1-144). Fund the throwaway with at least 0.1 SOL plus what the opt-in steps need.

## Stages
0. (j) P4.2 feed gap, before any trade (`feedGapThroughWsProxy` in `scripts/devnet_e2e_steps.ts`): the app's `PumpFeedListener` subscribes to the devnet pump program through a loopback WebSocket relay in front of the RPC's websocket (`wsEndpoint`), with the app's `WatchWindow` attached and the harness mint watched. The relay then blocks the websocket for 10 s (open connections cut, new ones refused before the upgrade). Pass lines: `(j) feed gap: listener ACTIVE through the loopback ws proxy`, `(j) feed gap: status left ACTIVE while the ws port was blocked` (`SOCKET_CLOSED/RECONNECTING`), `(j) feed gap: the watched mint is DEAD with FEED_GAP`, `(j) feed gap: ACTIVE again after the 10 s block`. Then the pump feed is started as `server.ts` starts it and every fetch for 12 s is recorded: `(j) boot: no pump.fun or DexScreener request` (boot mode `WS_ONLY`). Dry-run on the local validator: all five lines pass.
1. Simulate BUY with `sigVerify:false, replaceRecentBlockhash:true` (PumpCurveService LIVE state, calculateBuyQuote, txBuilder).
2. (a) BUY (scaled, see above) through the app's `executionCoordinator` singleton (the one server.ts uses; the harness no longer builds a second coordinator): sent through the RPC transport, CONFIRMED, db tokenQuantityRaw == on-chain ATA balance.
3. (b) close 50%. (c) close 100% (ATA closed, about 0.00203928 SOL rent back). Every signature is checked with getTransaction and printed as a Solscan `?cluster=devnet` link.
4. (d') forced revert through the app (`scripts/devnet_e2e_steps.ts`): after the 30 s per-mint cooldown from (a), one `executionCoordinator.executeTrade` buy runs with `PumpCurveService.calculateBuyQuote` wrapped by the harness so the quote's `maxInputLamports` (the max-SOL-in bound the pump buy enforces) is 1 lamport; the wrapper is restored right after. The app signs and sends it and the program rejects it (pump error 6002 on localnet). Pass: lifecycle REVERTED, the signature failed on chain (read by `readChainErr`: getTransaction retried with back-off through a 429 or an empty answer, then getSignatureStatuses with history search; when neither answers, the line says `on-chain error not read` instead of `err=undefined`), a REVERTED BUY transaction row, no position, and an immediate second buy refused with `Cooling down after recent execution failure (Ns remaining)` (the 15 s `cooldownAfterFailedTradeMs`) adding no row.
4b. (s) 3I, A1 (free, always runs, `unreadableReservesRefused`): built like (d'). Right after (d'), one `executeTrade` buy runs with `PumpCurveService.fetchPumpMarketState` wrapped so the coordinator's LIVE read of the harness mint comes back without `realTokenReserves` (SOL reserves kept), and `calculateBuyQuote` counted; both are restored right after. Pass lines: `(s) A1: LIVE buy with unreadable token reserves: reserves wrapper used`, `...: refused CURVE_PROGRESS_UNREADABLE` (lifecycle RISK_REJECTED), `...: nothing quoted or sent` (0 quote calls, no BUY row, no signature) and `...: no position`. Nothing is signed, and the refusal comes before the risk engine, so it starts no cooldown and can run inside (d')'s. Dry-run on the local validator: all four pass, and with the A1 check removed from the coordinator the refusal line FAILs.
5. (e') after that cooldown, two sequential `executeTrade` buys of the same mint: the first CONFIRMED, the second refused before anything is sent (`POSITION_ALREADY_OPEN`), exactly one open position; the harness then closes it so (f) starts flat.
6. (e'') P1.5: after the per-mint cooldown, one `executeTrade` buy whose `sendRawTransaction` the harness wraps once: the transaction is really sent, then the call throws (`fetch failed`), as a socket reset after forwarding does. Expected: the buy is not REVERTED, no REVERTED row exists for its signature, and the landed buy has one open position in the same process (at once when the confirm sees it, or through orphan recovery). The harness then closes it.
7. (g) P1.7: after the per-mint cooldown, one buy opens a position; the coordinator is then pointed (`setRpcEndpoint`, genesis check included) at a loopback proxy in front of the normal RPC that holds the first `getLatestBlockhash` for 20 s. `closePosition(STOP_LOSS)` must sell while that request is still held: the trading connection aborts it after `RPC_REQUEST_TIMEOUT_MS` (1.5 s) and asks again. The harness then points the coordinator back and closes anything left. The two-position form (a second position's stop sells while the first one's sell is held) runs on localnet in `tests/long/exit_concurrency.longtest.ts`; this harness trades one mint.
7b. (t) 3I, B7 and B10 (opt-in, `DEVNET_FEED_SWITCH=1`, `rpcSwitchMovesFeed`): the app's `pumpFeedListener` follows the coordinator as `server.ts` wires it (`follow(executionCoordinator)`), with the watch window attached. The coordinator is first pointed at R0, a loopback relay (HTTP on port P, its websocket on P + 1, as web3.js derives it) in front of the normal devnet RPC; the listener subscribes there and is ACTIVE. R0 then answers unsubscribes 2 s late (as a slow RPC does), and the harness calls `setRpcEndpoint(A)` (a second loopback relay) and, without awaiting it, `setRpcEndpoint(B)` (the normal RPC). Both switch notices reach the listener while it is still unsubscribing from R0, the case B10 fixed. The step counts live pump `onLogs` subscriptions per Connection by wrapping web3.js's `Connection.prototype.onLogs` and `removeOnLogsListener` for the step only. Pass lines: `(t) B7/B10: two quick RPC switches: listener ACTIVE on the coordinator's Connection (relay R0)`, `...: both switches succeeded`, `...: the switch is a feed gap (ENDPOINT_SWITCH, RECONNECTING)` (B7), `...: ACTIVE again`, `...: one live log subscription, on the coordinator's current Connection` and `...: no subscription left on an old Connection` (B10), `...: a launch made after the switch is watched` (a throwaway creator launches a coin; its key is on disk first and it is refunded after). An INFO line says which endpoint the coordinator ended on and how far apart the two notices were. Afterwards the coordinator is put back on the normal RPC (`...: coordinator back on its RPC` when it ended on A) and both relays are closed. Expected: the ENDPOINT_SWITCH gap releases anything the watch window was watching DEAD FEED_GAP; nothing else is watched at that point. Dry-run on the local validator: all lines pass; with B10's queue removed the two subscription lines FAIL (one subscription left on B), and with B7's RECONNECTING removed the gap line FAILs.
7c. (w) task 3K (opt-in, `DEVNET_FEED_WATCHDOG=1`, `deafSocketRecovers`, wired by `feedWatchdogStep`), right after (t): the app's `PumpFeedListener` and `WatchWindow` classes, new instances of the step's own (the app's singletons and the coordinator are not used), on a Connection whose websocket goes through a loopback ws proxy in front of the devnet RPC's. The listener is ACTIVE with its subscription confirmed, and a launch by a throwaway creator (key on disk first) is watched. The proxy then keeps the next socket deaf (it answers subscribes and drops every notification), and the listener is switched onto a Connection with that socket, as an RPC switch moves it; a probe entry is watched. Pass lines: `(w) feed watchdog: a deaf socket: listener ACTIVE through the loopback ws proxy, subscription confirmed`, `...: a launch before the socket goes deaf is watched`, `...: on a deaf socket after a switch, NO_DELIVERY gap, not ACTIVE` (within 30 s), `...: a launch watched on the deaf socket is DEAD with FEED_GAP NO_DELIVERY`, `...: ACTIVE again on a fresh socket`, `...: a launch after the move is watched`, then the creator's sell and refund lines. Every socket the step opened is closed, and the proxy too. Dry-run on the local validator: all lines pass; without feed-watchdog 0001 three lines FAIL (ACTIVE on the deaf socket with no gap, the probe still watched).
8. (h) P1.6 (opt-in, `DEVNET_DUMP_SOL`): a second throwaway wallet creates its own pump coin and seeds it; the app buys it (the creator and top-10 checks are waived for this coin, whose creator is the harness's own wallet). The harness then wraps the coordinator's `getMultipleAccountsInfo` so the next call naming the curve throws once (the app's own price read takes it), and the second wallet sells everything. Pass lines: `(h) ...: second wallet creates and seeds a coin` (it prints the seed and the projected price/entry after the dump, at most 0.72), `(h) ...: app buy CONFIRMED`, `(h) ...: the app's price read took the injected failure`, `(h) ...: dump visible below the -20% stop`, `(h) ...: STOP_LOSS sold within 10 s of the dump being visible` (expected about 3 to 6 s: the next one or two 3 s exit passes; before P1.6 the failed read put the mint in a 60 s back-off) and `(h) ...: the stop-loss sell succeeded on chain`. **The seed** (`dumpSeedPlan`): read from the coin's own curve after the create, constant product on its virtual reserves, so the price after the dump is at most 0.72 of the price before the app's buy, with a 15% margin. With 30 SOL virtual reserves that is about 6.3 SOL for a 0.02 SOL app buy; with the about 0.3 SOL virtual reserves the Mac run's devnet coin showed (a fixed 5 SOL seed hit `CURVE_NEARLY_COMPLETE`: it needed 1.0115e15 tokens and 7.931e14 remained), about 0.07 SOL. The step refuses, with the figure, a seed above `DEVNET_DUMP_SOL`, a seed that would take more than 95% of the tokens left, or a curve that would be within 5 points of the 60% curve-progress cap at the app's buy. **The second wallet**: its key is written to `<scratch>/second-wallet.json` (mode 600, next to the throwaway key) before any SOL is sent to it, and the coins it creates to `<scratch>/second-wallet-coins.json`. Every path, a failed create or seed included, ends with the app's position closed and the second wallet selling what it holds and refunding the harness wallet. A run with the same `APEX_E2E_SCRATCH` first sells and refunds whatever an earlier run left there, whether or not (h) runs; by hand, `solana transfer --keypair <scratch>/second-wallet.json <throwaway> ALL --url devnet` gets the SOL back. These are the only transactions the harness signs itself, all from its own throwaway wallets. Dry-run on the local validator (30 SOL curves, 0.02 SOL app buy): a refused seed refunded the second wallet to 0; the full step seeded 6.28 SOL, the dump showed price/entry 0.678, STOP_LOSS sold 3.0 s after it was visible, the second wallet ended at 0 and the harness wallet spent 0.17 SOL in curve fees.
9. (i) P4.1 (opt-in, `DEVNET_CLUSTER_CHECK=1`): the creator cluster and funder truth through the app's own pump log stream, watch window and funder lookup, which the harness wires to the coordinator's connection as `server.ts` does (it reads the window's snapshot, which is what `GET /api/watch` returns). The app itself trades nothing here. A fresh throwaway creator (funded from the harness wallet) launches its own coin with no dev buy and funds a throwaway W with 0.02 SOL; W buys 0.01 SOL and sells everything 25 s later. Then the creator launches a second coin and the harness wallet funds 5 throwaway wallets that buy it at once. Pass lines: `(i) creator cluster: the pump log stream subscribed`, `(i) creator cluster: the app's feed watches the creator's launch`, `(i) creator cluster: W's buy reached the window`, `(i) creator cluster: W (funded by the creator) sold at 25 s: /api/watch shows DEAD CREATOR_SOLD` (before P4.1 W's sell was not a creator sell and the launch stayed WATCHING), `(i) creator cluster: 5 wallets from one funder bought together` and `(i) creator cluster: 5 wallets from one funder: one cluster, not 5` (rawUniqueBuyers 5, uniqueBuyers 1, funderCoverage 1; on devnet the funder lookups may first see no signatures and retry after 1.5, 4 and 10 s, so allow up to 30 s). Every throwaway wallet sells what it holds and refunds the harness wallet. Dry-run on the local validator: all six lines pass, about 0.03 SOL spent. The same two cases run against the real server on localnet in `tests/long/creator_cluster.longtest.ts`. Note: on the local validator a pump `create_v2` named `P41A harness` (12 characters) fails with `InsufficientFundsForRent`, while 11-character names work, so the harness names its coins `P16 harness` / `P41 harness`.
9a. (u) 3I, B3 (opt-in, `DEVNET_SELLER_NEVER_BOUGHT=1`, `sellerWhoNeverBought`, wired as (i)): a seller that never bought, the case cloud patch B 0004 was written for. A throwaway creator launches a coin with no dev buy and sends a throwaway W 0.02 SOL (W's first incoming transfer, so the creator is W's funder). A throwaway X, funded by the harness wallet, buys 0.01 SOL and SPL-transfers all its tokens to W (`ChainKit.transferTokens`: W's associated token account is created by X, Token-2022 or SPL as the coin uses); W sells them. Pass lines: `(u) B3: the pump log stream subscribed`, `(u) B3: a seller that never bought: the app's feed watches the launch`, `...: X's buy reached the window`, `...: W got X's tokens by transfer, without buying; the launch still WATCHING` and `...: W (funded by the creator, never bought) sold: /api/watch shows DEAD CREATOR_SOLD` (the reason names W). W, X and the creator are created (keys on disk) before any SOL moves and all sell what they hold and refund the harness wallet at the end, a failed refund being a FAIL line. On the public devnet RPC the seller lookup may need its retries (1.5, 4, 10 s); the step waits up to 45 s. A feed gap during the step releases the launch DEAD FEED_GAP instead, which FAILs the last line for a reason that is the socket, not B3: re-run it. Dry-run on the local validator: all lines pass; with the seller lookup removed (`askSellerFunder` a no-op) the launch stays WATCHING and the last line FAILs. Step (m2) (DEAD `SELLER_FUNDER_UNKNOWN`) is held: that rule was replaced by B 0004's softer one.
9b. (k) P4.3 (opt-in, `DEVNET_RELEASE_GATES=1`, function `releaseGatesOnChain`, wired by `releaseGatesStep` in `devnet_e2e.ts`): the release gates through the app's own log stream, watch window and auto controller (`attachWatchWindow`), wired as `server.ts` wires them, curve progress included. LIVE is disarmed for the step (PAPER auto needs the coordinator in PAPER) and re-armed after it. For SHADOW, then for PAPER, a throwaway creator launches two coins 1 s apart and 10 throwaway wallets buy 0.01 SOL of each; both are released READY (concentration and flow pass) about 1 s apart and reach the controller by themselves. Pass lines: `(k) release gates: the pump log stream subscribed`, `(k) release gates: SHADOW: 10 equal buys of <mint>` (twice), `(k) release gates: SHADOW: both launches released and journaled`, the same two for PAPER, `(k) release gates: SHADOW and PAPER decision rows match` (WOULD_BUY and BOUGHT count as one, numbers in the reason are ignored; expect both REJECTED at the score stage, since a devnet curve's score is far below 70) and `(k) release gates: every decision row carries passingSignals`. With `DEVNET_CURVE_CAP=1` a third coin is pushed by one throwaway wallet to the cap plus 2 points (62% of its tokens sold): `(k) curve cap: pushed past 60% inside the window: /api/watch shows DEAD CURVE_TOO_FAR`, `(k) curve cap: the journal rejects it at the watch stage (WATCH_DEAD: CURVE_TOO_FAR)` and `(k) curve cap: a LIVE buy is refused on the coordinator's fresh read (CURVE_PROGRESS_TOO_HIGH), nothing sent`. Why so much SOL: progress is the share of the curve's 793.1M tokens sold; on a fresh curve with 30 SOL / 1,073M virtual reserves, 60% sold needs about 23.9 SOL into the curve (24.2 SOL with the buy fee) and 62% about 25.8 SOL. If the devnet Global still has the 1 SOL initial virtual reserves the localnet accounts were dumped with, the same push costs about 0.86 SOL; the step reads the coin's own reserves and prints the figure it needs. Not dry-run on the local validator yet (the dry-run was not allowed in the session that wrote it).
9c. (n) 3C (opt-in, `DEVNET_LOSS_FLOOR=1`, `lossFloorLatch` and `bootRefusesBadLimit`, wired by `lossFloorStep`), after the per-mint cooldown from (g): the net daily PnL floor over a rolling 24 h, its latch and the two resume flags, through the app's own `executeTrade` on the harness mint. The floor is `MAX_DAILY_LOSS_USD`, changed in-process with `executionConfig.updateConfig` (the env's own check runs, the USD-to-SOL conversion is the live one, nothing is pinned) and put back after. Pass lines, all prefixed `(n) 3C: net daily PnL floor:`: `buy under a roomy floor CONFIRMED` (floor above the window's net PnL plus three orders), `full sell`, `the round trip lost its fees` (the window's net PnL before and after), then, after the per-mint cooldown, `floor $X below the window's loss: refused DAILY_LOSS_LIMIT, nothing sent, latched`, `floor raised back: still refused, latched`, `clock past the next 00:00 UTC (+N h): still refused, latched` (Date.now is offset for that one `executeTrade`, and the SOL price is read for real under that clock, two sources agreeing, so LIVE does not refuse a stale price first; the clock is put back and the price read again right after. If the price sources do not answer, this line FAILs with a SOL price refusal, which is the network, not 3C), `the refusal says when the oldest loss leaves the window`, `resume {clearHalt}: still refused, latched`, `resume {clearDailyLossLatch} with the window below the floor: refused and latched again` and `clearDailyLossLatch cleared the latch before that buy`. Then a child process boots `server.ts` under the devnet guard with `MAX_POSITION_SIZE_SOL=abc`: `(n) 3C: boot with MAX_POSITION_SIZE_SOL=abc refuses before any RPC call` (non-zero exit, the startup message, no `[devnet-guard] allow` line, no DB file). Afterwards MAX_DAILY_LOSS_USD is back and the latch is clear, so (e''') can buy. "Nothing sent" is checked as no new BUY row and no signature; the step does not read the reservation figure. Dry-run on the local validator: all lines pass; with the latch removed from the risk engine the latched lines FAIL, and with the boot check removed the boot line FAILs.
9d. (l) 3A (opt-in, `DEVNET_READINESS_GATE=1`, `readinessGateAfterMismatch`, wired by `readinessGateStep`), after the per-mint cooldown from (n): with LIVE armed, an unresolved LIVE BUY row (RECONCILIATION_REQUIRED, a made-up signature for a made-up mint) is written into this run's scratch database and Reconcile is run (`startupReconciliation({ fresh: true })`, what the Reconcile button runs). Pass lines, all prefixed `(l) 3A: per-buy readiness:`: `Reconcile with an unresolved LIVE buy row: RECONCILIATION_MISMATCH naming it, LIVE still armed`, `buy while reconciliation is at MISMATCH: refused LIVE_NOT_READY, nothing sent` (RISK_REJECTED `LIVE_NOT_READY: ... startup reconciliation is RECONCILIATION_MISMATCH`, no BUY row, no signature, no position), then the row is marked REVERTED and `Reconcile after the row is resolved: EXECUTION_READY`, `buy after EXECUTION_READY: CONFIRMED` and `sell back`. Each buy runs after a balance sync that answered, and a buy refused INSUFFICIENT_SPENDABLE_BANKROLL for a lost balance read is retried (as in (n)); each Reconcile is retried twice (2 and 4 s) while what keeps it from the expected status is not the planted row. A check the RPC kept from being made is a `SKIP` line with the reason, not a PASS and not a FAIL. Afterwards the row is resolved and Reconcile run again, so (e''') starts ready. Dry-run on the local validator: all lines pass, with two HTTP 429s on the balance read and one failed wallet token scan injected; with both of 3A's checks removed the refused-buy line FAILs (the buy is CONFIRMED, then sold), and with only the first removed it FAILs too (the send-time re-check refuses `ENTRY_REVOKED`, nothing sent, but the line asks for the refusal at the start of the buy).
9d. (m) 3B, task 3K (opt-in, `DEVNET_SESSION_SPEND=1`, `sessionSpendMatchesWallet`, wired by `sessionSpendStep`), after (n): a 5-buy DEVNET_LIVE auto session through the app's own auto controller (`submitCandidate`) and coordinator, signed by the harness wallet. ## Tracing and output
- `APEX_TRACING=true` works here: the harness starts tracing before it makes any connection, as `server.ts` does (the local-only OTLP rule still applies; see the tracing notes in the README).
- With `APEX_VERIFY_BLOCKHASH=true` the log shows `[S210] independent blockhash check passed for the BUY` when the check ran.
- Everything printed goes through a redactor, and the devnet guard prints a private RPC host as `<rpc>`. When the crash-after-submit child does not reach the send, step (f) says how it ended and shows its last lines instead of a raw dump.

## Which mint it trades
The app's eligibility filter refuses a creator holding over 5% or a top-10 share over 20%, and devnet test mints often fail that. So the harness probes mints (the listed ones, then the pump program's recent activity, at most 25) until one clears both limits, and uses it. It builds the eligibility report itself from fresh holder data just before the buy, with the app's own `EligibilityFilter`, so a rate-limited lookup inside the coordinator cannot refuse a mint it already screened.
If none clears, it falls back to the readable mint with the lowest creator share and **waives only the creator and top-10 checks, in the harness's report, logging `WAIVER` lines with the real values**. The app's filter is not changed. A share it could not read is never waived, and neither is any other failed check. The mint is saved in the scratch directory so the crash and recover processes use the same one.
