# Apex Quant - Solana Pump.fun Trading Workstation

A full-stack workstation and automated execution engine for Pump.fun bonding-curve tokens on Solana. One `ExecutionCoordinator` owns every trade; risk gates, on-chain reconciliation and a persisted halt sit behind it. **Devnet and localnet only**: the cluster guard refuses mainnet.

> **Status: not live-ready, and no evidence of a profit. Devnet only.** Everything runs in PAPER mode and is covered by tests, and the full flow runs against an in-process LiteSVM validator (`npm run localnet:e2e`). The devnet harness (`npm run devnet:e2e`) has passed on real devnet: a manual round trip on 2026-10-10 through the app's own API and dashboard (0.01 SOL buy, 50% sell, 100% close of a Token-2022 pump coin; recorded quantity matched the chain at each step; token account closed), and, on 2026-10-26, the **Stage 3 gate**: the unit, long and localnet suites, harness steps (l) to (p) (readiness per buy, session spend, loss floor, kill switch surviving a restart, no re-entry), and a 50-minute seeded DEVNET_LIVE session (5 auto buys, never more than one open position, no halt, spent SOL equal to the wallet's drop, all 16 signatures finalized, 0.0476 devnet SOL spent). That session's price moves came from the harness's own mover wallet, so its +0.0029 SOL result says nothing about the strategy: the gate proves the machinery, not an edge. The edge search ended the same day. On the public 39-day corpus the best an entry could do (buying every launch right after its first recorded trade, with the real exits) was gross about zero and net -2% to -4% per trade after the 1.25% pump fee each side and the transaction fees. The only room found was in hindsight exit timing, and the best simple rule that tries to capture it (a full exit at about +4%) lost on train (-5.75%) and on a fresh, never-seen set (-6.84%, 90% interval -16.3% to +0.1%). On live-like data the live gate admits roughly one launch in 40,000. See [`KNOWN_RISKS.md`](KNOWN_RISKS.md) section 11. The devnet runs need `MIN_LIQUIDITY_USD=5`, because devnet curves hold only a few dollars and the $2,000 default rejects them all; that override is honoured on devnet and localnet only and ignored on mainnet-beta. An earlier 30-minute DEVNET_LIVE auto-snipe window placed no trades: every devnet launch it watched was rejected (creator sold, no trades, or score far below 70). The full harness reports and the Stage 3 gate report are kept in the project folder (`notes/stage3-gate-report.md`, `notes/kill-tests.md`), not in this repository. Do not fund a mainnet wallet for this system. What the tests do and do not prove is in [`docs/TEST_FIDELITY.md`](docs/TEST_FIDELITY.md); open decisions and unverified items are listed under "Needs Mike" in the overnight patch `INDEX.md`. What score auto can realistically reach (72-76 at best, 62-68 typical) and why the seeded devnet token will not be bought are in [`KNOWN_RISKS.md`](KNOWN_RISKS.md) section 8. This is not a latency-sensitive HFT system: there is no measured latency advantage, kernel bypass or co-location in the code, and the corpus tests above found no entry speed that makes the strategy profitable.

## 🔒 Critical Safety & Architecture Principles

1. **Authoritative Execution Pipeline**: All trading paths (UI manual terminal, social signals scanner, Pump.fun hot callouts, and autonomous snipers) delegate exclusively to the central `ExecutionCoordinator`. No external component or background loop may independently generate or mutate positions.
2. **Safe Default (PAPER Mode)**: The engine starts in **PAPER simulation**; auto trading starts **OFF**. A live buy needs an explicit arm.
3. **Cluster guard (devnet or localnet only)**:
   - `ALLOWED_CLUSTER` defaults to `devnet`. Before any send the RPC's genesis hash must match the allowed cluster; a mainnet RPC URL or a mainnet genesis is refused, and the check fails closed if the genesis cannot be read. A `mainnet-beta` value of `ALLOWED_CLUSTER` is accepted only so a read-only server can watch mainnet; while it is set, arming LIVE, `executeTrade` and every send refuse (`assertSendClusterAllowed`). `ALLOWED_CLUSTER=localnet` (needs `LOCALNET_GENESIS_HASH`) is allowed for a local validator. There is no mainnet auto mode; only a read-only server should use a `mainnet-beta` cluster value.
   - The database file remembers the genesis hash of the first verified RPC (`cluster_genesis_hash` in `app_settings`). After that, an RPC on another cluster fails the cluster check with `DB_CLUSTER_MISMATCH`, so that ledger is never reconciled or traded against another chain. To change clusters, point `APEX_DB_PATH` at a new file.
   - A wrong-cluster RPC is also refused at arming time (`GET /api/execution/can-arm`), not only at the first send.
4. **Strict live safeguards**:
   - The `ALLOW_LIVE_REAL_MONEY_TRADING` switch must be on before any send (the name is historical; on this project it gates devnet and localnet sends, nothing else). The in-process test harnesses turn it on only after asserting the cluster genesis; the repository's `.env.example` leaves it off.
   - Arming: `POST /api/execution/arm` with confirmation code `CONFIRM_LIVE_TRADING_RISK`, a loaded keypair in `READY` status, RPC health `HEALTHY` on the verified cluster, and no halt.
   - Hardened pre-trade risk limits (daily loss, exposure, slippage, priority fee caps) must pass. Live trades need real on-chain quotes; synthetic prices are refused.
   - **Kill switch**: `POST /api/execution/kill-switch` with an explicit `{"activate": true|false}` (anything else is a 400). The header button sends the state it means: a press while the switch is off sends `true`; RESUME asks for a confirm first, and a RESUME press within 2 s of the switch turning on is ignored, so a double tap of the emergency stop leaves it on. Activating it also disarms live trading and sets auto OFF (after any buy in flight); resetting it turns neither back on. The switch is held in memory, so a restart clears it; the next boot then raises `KILL_SWITCH_WAS_ON` and LIVE refuses to arm until `POST /api/auto/resume {"clearHalt":true}` clears it. `POST /api/wallet/panic-liquidate` and the WebSocket `PANIC_LIQUIDATE` run the same stop and then sell every active position. Telegram `/panic_sell` runs the same code, but do not count on it in an emergency: Telegram cannot deliver it (no webhook is registered with Telegram and nothing polls for updates), so it runs only when something posts it to `POST /api/telegram/webhook` with the operator token. `POST /api/execution/close` always closes with the reason `Operator close` (the client's `reason` text is kept only as a journal note). A close that sold nothing now says so: its result carries `outcome` `ADOPTED_EARLIER_SELL` (an earlier sell that landed unconfirmed was adopted; `status` may still be `PARTIALLY_CLOSED` with tokens left), `ADOPTED_EARLIER_SELL_FILL_UNREAD` (the same, with the fill unreadable, so no PnL was recorded) or `ASSUMED_LOSS_EMPTY_WALLET` (the wallet held none, so the row was closed and its cost basis booked as an assumed loss), and the Plug & Play and Sniper close messages say which instead of "Closed 100%".
   - **Persisted halt**: a halt (for example an unexplained wallet balance change) survives a restart. While halted, buys are refused and the can-arm reasons say why; protective exits (stop-loss, trailing stop, manual close, panic) still run. An operator clears it with `POST /api/auto/resume {"clearHalt":true}`.
5. **Post-Trade On-Chain Reconciliation**: Positions are constructed from verified on-chain transaction outcomes and actual balance changes, not pre-trade estimates.
6. **Operator Authentication**: every `/api` route except `GET /api/health` and `POST /api/auth/login` requires an operator token (deny by default; the path is normalized first, so case, encoding and absolute-form tricks do not bypass it). The token is `OPERATOR_AUTH_TOKEN` (16+ characters); `OPERATOR_PASSWORD`, if set, enables password login that returns a session token. The server binds to loopback unless `ALLOW_PUBLIC_BIND=true` (then `BIND_HOST` is honoured).

## 🚀 Quickstart: Run Locally

### Option 1: Run with Node.js (Local / VPS)

**Prerequisites:** Node.js >= 22.5.0 and npm >= 10.0.0 installed (Node.js >= 22.5.0 is strictly required for native `node:sqlite` database persistence).

```bash
# 1. Install dependencies
npm install

# 2. Build production frontend & server bundle
npm run build

# 3. Start the production server
npm start
```
`npm start` runs the bundle `dist/server.cjs`, which always runs in production mode (it sets `NODE_ENV=production` itself when it is unset, and says so) and serves only the built `dist/` folder. The Vite dev middleware, which serves the project folder, runs only under `npm run dev` (`server/system/runtimeMode.ts`).

Open [http://localhost:3000](http://localhost:3000) in your browser.

**One server per database and per wallet.** Every guard against selling or buying twice lives in the server's memory, so two servers on one database or one signing key would both sell the same stop-loss. The server takes a lock file next to the database (`<APEX_DB_PATH>.lock`) before anything else starts, and one per signing key in `~/.apex/locks` (`APEX_LOCK_DIR`). A second server on the same database, port or key prints `INSTANCE_LOCKED` or the listen error and exits with code 1 before it reconciles, runs the exit loop or restores the auto mode. A lock left by a process that is no longer running is taken over on the next start. Each lock carries a random per-boot id and a heartbeat the holder rewrites in place every 5 s (never by renaming a temp file over it: on an rclone FUSE mount that made a released lock come back seconds later), and a lock written by another boot with a heartbeat under 30 s old is refused whatever its pid (in Docker every server is PID 1, so a second container on the same `apex-data` volume, for example from `docker compose run`, is refused too). After a container crash the restarted server therefore waits until the old heartbeat is 30 s old; the restart policy retries it. A server that no longer holds a lock it started with (removed by hand, taken over, or its heartbeat not written for 25 s, for example on a failing mount, and not writable at the moment of the check either) signs nothing more: each buy and sell is refused `INSTANCE_LOCK_LOST` before it is signed. For a second copy (a smoke test, a scratch run) use its own scratch folder, database and throwaway key: `npm run smoke` does this.

For live development with hot reloading:
```bash
npm run dev
```
The dev server serves the project folder, so it answers 404 for secret and state files (`server/security/secretPaths.ts`): the name patterns (`.env*`, `env.txt`, `*keypair*.json`, `*.db`, logs, ...) and, by path, the configured `SIGNER_KEYPAIR_PATH`, `APEX_DB_PATH` (with its `-wal`, `-shm` and `.lock` files) and env file (`APEX_ENV_FILE`, else `.env`). Every match ignores case.

### Option 2: Run with Docker / Docker Compose

**Prerequisites:** Docker and Docker Compose installed.

```bash
# Compose refuses to start without an operator token (16+ characters). Put it in your shell or in .env next to docker-compose.yml.
export OPERATOR_AUTH_TOKEN=$(openssl rand -hex 32)

# Build and launch container in background
docker compose up -d --build

# View real-time logs
docker compose logs -f

# Stop the container (the data volume is kept)
docker compose down
```

What to expect from the container:
- The dashboard is at <http://127.0.0.1:3000>, published on the host's loopback only.
- It is devnet-only and starts in PAPER with no signer: compose passes a fixed list of variables (see `docker-compose.yml`) and does not load `.env` as a whole, so `OPERATOR_PRIVATE_KEY`, `SIGNER_KEYPAIR_PATH` and other `.env` settings outside that list do not reach it. A key generated or imported in the UI is saved in the volume.
- The database (and any such key) lives in the named volume `apex-data`, mounted at `/app/data`. It survives `docker compose down` and rebuilds; `docker compose down -v` deletes it.
- The image only runs the app. Tests and the localnet scripts (`npm run localnet:e2e` and friends) need `solana-test-validator` and the dev dependencies, so run them on the host.

## ⚙️ Configuration (`.env`)

Copy `.env.example` to `.env`:

```bash
cp .env.example .env
```

Key environment variables. [`docs/ENV.md`](docs/ENV.md) lists every variable the server reads, with defaults and devnet-safe values (a test keeps it in step with the code); `.env.example` is the starting file:
- `PORT=3000`, `BIND_HOST` / `ALLOW_PUBLIC_BIND`: port and bind address (loopback by default)
- `OPERATOR_AUTH_TOKEN`: operator API token (min 16 characters; `openssl rand -hex 32`). If unset (or shorter than 16 characters, which is ignored with a boot warning), a volatile token is generated and printed at startup (not printed in a container). The primary token never expires; a restart or a rotate replaces it. Never commit it. `OPERATOR_PASSWORD` optionally enables password login.
- `ALLOWED_CLUSTER`: `devnet` (default) or `localnet` (with `LOCALNET_GENESIS_HASH`). LIVE arming, trading and sending on mainnet are refused. `mainnet-beta` is accepted only so a read-only server can watch mainnet.
- `SOLANA_RPC_URL`: `https://api.devnet.solana.com` or a loopback URL for a local validator. The websocket address is derived from it; `SOLANA_WS_URL` is not read by the server.
- `ALLOW_LIVE_REAL_MONEY_TRADING`: leave `false`; only the devnet harness sets it, in-process, after checking the genesis hash.
- `SIGNER_KEYPAIR_PATH`: keypair file (default `.apex_trading_keypair.json`, mode 0600). Use only a throwaway devnet key. `OPERATOR_PRIVATE_KEY` / `SOLANA_PRIVATE_KEY` override it and are better left unset.
- `JITO_BLOCK_ENGINE_URL`: leave unset on devnet/localnet (there is no devnet block engine; devnet and localnet send plain transactions). `DEFAULT_JITO_TIP_SOL` is the fallback tip (default `0.00018`, capped at 15% of trade notional); the tip floor is `MIN_JITO_TIP_SOL` (default `0.00015`), and the coordinator forces the tip to 0 while Jito is off.
- `AUTO_SNIPE_ENABLED=true`: required before the auto-snipe pipeline will run at all (default off; the controller then still starts in mode OFF).
- `AUTO_MANAGE_RECOVERED=true`: let the exit ladder manage positions rebuilt after a restart. Default off: recovered positions only get the hard stop.
- `PAPER_BANKROLL_SOL` (default `0.07`), `PAPER_STRICT_GATES=1` (paper rejects unverified safety checks like LIVE; without it, paper still refuses a buy whose holder read was made and failed or timed out, and fills a buy whose curve could not be read at all on the flat model, marked unverified), `CAPITAL_TIER` (`MICRO_10` or `INSTITUTIONAL`).
- `DEMO_MODE=true`: loads fake callers and synthetic social data; never use it for anything but a demo. LIVE cannot be armed while it is on.
- `APEX_ENV_FILE`: if set (even to an empty string) it replaces `.env`, so scripts and tests that spawn the server never read the real one. `APEX_DISABLE_EXTERNAL_FEEDS=true` stops outbound market feeds (used by smoke).
- `GEMINI_API_KEY`: optional, for AI diagnostics.
- `APEX_READ_ONLY=true`: watch-only mode (see "Read-only mode" below).
- `CONFLUENCE_MIN_SCORE`: starting value of the confluence buy threshold, a whole number 0 to 100 (default `70`); the operator can change it at runtime (see below).
- `MIN_LIQUIDITY_USD`: eligibility floor in USD (default `2000`). Honoured on devnet and localnet only; ignored on mainnet-beta.
- `MAX_POSITION_SIZE_SOL`: upper limit for any single order, including the editable snipe amount and auto order size.
- `APEX_RECORD_MINT_MINUTES`, `APEX_RECORD_MAX_TRADES_PER_MINT`, `APEX_RECORD_RETENTION_DAYS`, `APEX_RECORD_MAX_ROWS`: how much the launch recorder keeps; `APEX_REPLAY_MAX_LAUNCHES` (100 to 50000, default 5000) caps one replay.

## 🛡️ Security Hardening

What the code does, and where the limits are:

- **CORS and WebSocket origins**: REST requests are allowed from `localhost`, `127.0.0.1`, the request's own host, and origins listed in `ALLOWED_ORIGINS` (`server/middleware/auth.ts`). Other origins get no CORS headers. The `/ws/engine` socket takes frames of at most 64 KiB (`WS_MAX_PAYLOAD_BYTES` in `server.ts`; a larger one closes it with 1009), and a socket that sends anything but `AUTHENTICATE` before it has authenticated is closed with 4002.
- **Circuit breaker**: the risk engine opens the breaker and turns the kill switch on after 3 consecutive failed wallet-balance reads (`server/risk/riskEngine.ts`), and refuses buys once the net PnL of the last 24 hours (not since UTC midnight) reaches the floor set by `MAX_DAILY_LOSS_USD`; that refusal latches, per mode and across restarts (it is saved in the database), until an operator sends `POST /api/auto/resume {"clearDailyLossLatch":true}`, which clears the latch of the mode the coordinator is in now (LIVE or PAPER, never both), a flag separate from `clearHalt`. Only an operator closes the breaker: a kill-switch reset closes it once the latest balance read has succeeded.
- **Keypair file**: `.apex_trading_keypair.json` is written with POSIX `0600` permissions, and the app checks `.env` and the keypair for looser permissions. Use a throwaway devnet key only.
- **Audit trail**: auto decisions and trade records are rows in the SQLite database; see [`KNOWN_RISKS.md`](KNOWN_RISKS.md) section 10 for its limits.

## 🏠 Home page and auto-snipe

- The home page is the Pump.fun token board: **New launches / Watching / Holding**, a SOL wallet strip, a bonding-curve depth ladder and trade tape for the selected token, and the auto-snipe panel. Unknown values show "—".
- **What could not be read says so.** After a 401 or with the server unreachable, Plug & Play says its positions, events and public key were not read (not "No positions opened yet" / "None"), the Tracker's signal count reads "not read", the board counts read "—" until the first board, the Auto panel and header badge mark a status older than 15 s or whose last read failed as STALE, the read-only strip turns amber "LAST KNOWN" once the mode answer is stale, and "WS STREAMING" needs a message in the last 30 s, not only an open socket. KILL AUTO stays enabled: it is an emergency control and the server answers it.
- **Alerts and the kill switch say what the server holds, or that it cannot be read.**
  - After logout or a 401 the server's operator alerts leave the alert dock; they come back with the next read under a valid token.
  - System checks shows every row UNKNOWN (greyed, with the last value and its age) while its read fails.
- **Exits are announced.** The dashboard compares the open positions every 5 s; a position that was sold (by the exit engine or by hand) raises an alert with the share and token quantity sold, the exit reason and the realized PnL. Plug & Play's journal rows for sells show the share, quantity, price and PnL.
- **Every sell button asks first.** Close (Plug & Play), Take 50% and Dump 100% (Sniper holdings) confirm with the mode, the share and the token quantity they sell and the holding's value at the last mark (the sale fills at the market). A partial sale reports "SOLD n% (position still open)", never "POSITION CLOSED", and the holdings show the tokens held.
- **Every confirm is a dialog that Enter cannot accept**: PANIC, KILL AUTO, the header RESUME, every sell button and every LIVE snipe warning. The dialog opens with Cancel focused; its red button takes a click (or Space once tabbed to), and Escape cancels. Every modal is a dialog that keeps Tab inside it; from Plug & Play and the sniper, Tab also reaches the header KILL SWITCH.
- **A panel that fails to render does not take the header with it.** Each panel and modal has its own error boundary: the one that threw is replaced by a notice, and the header and KILL SWITCH stay. If the whole dashboard fails, a bare KILL SWITCH that still posts to the server is shown. The Auto panel accepts a reply's `status` only when it is a status object (a refusal carries `status: "REJECTED"`).
- **Open LIVE positions are shown whatever the mode.** A kill switch, panic, DISARM or an auto trigger sets the server to PAPER while real LIVE positions stay open (their exits keep running). `GET /api/wallet/state` then lists them in `activePositions` (each row has its `executionMode`) and totals them apart in `liveOpen` (count, open PnL, today's realized LIVE PnL); the header shows a red "LIVE n open" chip at every width, Sniper holdings label each row LIVE or PAPER, and Telegram `/positions` labels each row and totals LIVE apart from PAPER.
- **Every figure says how old it is.** The wallet strip shows when the balance was last read (it is a cached read, refreshed every 10 s by the wallet sync loop and after trades; "last read FAILED" when the latest read failed) and the SOL/USD reading's age, STALE past 120 s (USD figures still use it; LIVE sizing refuses a stale price). The Holding table and the Plug & Play blotter show each mark's age, STALE past 15 s (the coordinator's `MARK_STALE_MS`). The header PnL pill says STALE when its last fetch failed or is over 10 s old. Open PnL is at the curve spot price with no exit fee, price impact or tip taken off, and USD PnL is SOL PnL times today's SOL price; the labels say so.
- Auto trading is owned by one controller (`server/auto/controller.ts`), **OFF at every start; the confluence threshold comes back on restart, the mode does not** (the saved mode is only reported in the startup note, and a restart never resumes sending, paper or live: set the mode again after looking at the state, and DEVNET_LIVE needs LIVE armed and its confirmation code; after a kill, the kill is saved first and auto stays OFF and killed after a restart until the operator sets a mode). `NEGATIVE_EXPECTANCY` and `LOSS_STREAK` look at the last 20 closed auto trades across sessions; after one trips, setting PAPER or DEVNET_LIVE is refused (`LOSS_TRIGGERS_NEED_ACK`) until `POST /api/auto/resume {"ackLossTriggers":true}`, and trades closed before that no longer count. `WALLET_UNKNOWN` fires after 10 s with no good balance read. Every LIVE buy, manual included, is also refused (`LOSS_TRIGGERS`) while `NEGATIVE_EXPECTANCY` or `LOSS_STREAK` holds over the last 20 closed LIVE trades (manual and auto) since the last `ackLossTriggers`, and, once 25 LIVE trades have closed, when the raw Kelly over the last 25 closed LIVE trades is at or below zero (`NEGATIVE_RECENT_EXPECTANCY`, `CapitalSizer.KELLY_RECENT_WINDOW`), on top of the lifetime Kelly check. The order size, session budgets and callout rules are still in memory only. Change mode with `POST /api/auto/mode`, stop with `POST /api/auto/kill` (optionally `exitAll`, which sells every auto-owned position, including an auto buy that returned unresolved and was adopted later; the reply counts `attempted` and `closed`, lists `refused` (nothing sent) and `failed` sells, gives `stillOpen`, the auto positions left open (with or without `exitAll`), and `manualOpen`, the positions you opened by hand, which KILL AUTO never sells (the reply's `note` says so), and is `success:false` when any sell was refused or failed or anything auto bought is still open; the Auto panel shows the same). Modes: `OFF`, `SHADOW` (all gates, journals "would buy", nothing sent), `PAPER`, `DEVNET_LIVE` (devnet only, 0.005 SOL per order unless the operator changes it, one open position, needs `ALLOWED_CLUSTER=devnet`, the coordinator armed LIVE and the confirmation code). There is no mainnet auto mode. It needs `AUTO_SNIPE_ENABLED=true`.
- **Order sizes are editable.** One saved **snipe amount** sizes every manual snipe (default 0.01 SOL, minimum 0.001 SOL, at most `MAX_POSITION_SIZE_SOL`; `GET /api/snipe/limits` returns the limits). The auto trader has its own **order size** (`POST /api/auto/order-size`, default 0.005 SOL) that applies in PAPER and DEVNET_LIVE alike, so paper results match what live would do. An out-of-range value is refused with a reason, never clamped. Every number box on the dashboard takes a dot as the decimal mark: "2,5" is refused with that reason rather than read as 25. Auto order size and budget are kept in memory and reset at restart.
- **Session spend cap.** `POST /api/auto/budget` edits the session budget. A DEVNET_LIVE session defaults to 5 buys and 0.02 SOL including fees. A PAPER session may turn its bankroll over: up to 50 buys and 10 times `PAPER_BANKROLL_SOL`. A PAPER limit never carries into real SOL.
- **PAPER auto-restore.** If a PAPER session is dropped to SHADOW only because readiness turned red, it comes back to PAPER by itself after readiness has stayed green for 60 seconds. Any other cause, and any operator choice, cancels the pending restore. DEVNET_LIVE is never restored automatically.
- **One confluence threshold.** The watch window's HOT gate, the buy gate and manual snipes all read the same score threshold. Its starting value is `CONFLUENCE_MIN_SCORE` (default 70); the operator changes it with `POST /api/auto/threshold` or the Auto panel (whole number 0 to 100, saved and restored after a restart, and the panel warns below 50). A lower threshold means more buys of weaker coins. See [`KNOWN_RISKS.md`](KNOWN_RISKS.md) section 8 for the scores that are actually reachable.
- Candidates must come out of the watch window (20-120s of real trade events) before any gate runs. Every decision, accept or reject, is a row in the `decisions` table with its reason and the release's `passingSignals`.
- **Release gates (P4.3).** A `READY` release (the window ran out without a HOT verdict) is bought only with concentration passing and at least 2 strong signals (`READY_TOO_WEAK` otherwise), and the `DEVNET_LIVE` auto mode never buys a score below 50 (`CONFLUENCE_DEVNET_LIVE_FLOOR`), whatever the threshold. The floor is an auto-buy gate only: a manual snipe, LIVE armed or not, is held to the plain threshold. A launch past 60% of its curve (tokens sold; `APEX_MAX_CURVE_PROGRESS_PCT`) is not bought: the window releases it `DEAD` `CURVE_TOO_FAR`, the controller drops a release past it (stage `curve`) and the coordinator refuses it on its fresh curve read, manual buys too. A release is a signal for 8 s in every mode, SHADOW included (`STALE_SIGNAL`); a queued release is kept 6 s. A refusal that only says "not now" (a cooldown, a stale read) no longer burns the mint for the session, and a watch release refused that way is tried again 2 s later while it is fresh. `npx tsx scripts/recorder_backtest/ready_strength.ts --recorded <db|jsonl>` prices the READY entries the new rule refuses against HOT entries on the app's own recordings. The recorder studies in `scripts/recorder_backtest/` (`late_rule.ts`, `ready_strength.ts`, `exit_variants.ts`, `realistic_ev.ts`) load the recorder's `MARKER` rows and cut a launch at the first restart or feed gap inside it, as the in-app replay does (`cutAtRecordingGap` in `recorded.ts`); `late_rule.ts` counts the cut launches as `recordingGap`.
- **The creator cluster is not demand.** In the watch window the creator, the create signer and every wallet funded by one of them form one cluster. "Funded" is any SOL source in the wallet's history: a wallet with at most 8 signatures has every transaction read (each transfer into it, and any other wallet that paid the fee of a transaction it signed), a longer history only its oldest one. Every buyer count is a count of clusters: wallets that share any SOL source are one buyer, and every wallet whose history was not read in full, or that shows no SOL source at all, counts with all the others like it as a single buyer. Velocity needs five distinct clusters buying in the last 30 s and counts each one up to 0.25 SOL per 30 s; flow needs five distinct buying clusters, more than the selling ones (trades are reported apart). The same single-buyer rule holds there: every buyer that is not independent (no SOL source found, a history not read in full, or a lookup that failed) counts with all the others like it as one buying cluster, and a launch is held in the window while a buyer's funder lookup is outstanding, as for a seller. A replay of recordings without funder history (the HF corpus) still counts such wallets apart, so it overstates velocity and flow against live. Their trades are left out of velocity, flow and net inflow (the board's net inflow column is the organic figure; `/api/watch` reports the cluster's own SOL as `creatorClusterBuySol` / `creatorClusterSellSol`), and a sell by any of them releases the launch `DEAD` with `CREATOR_SOLD`, also when the funder that ties a seller to the creator is learned after the sell. Funder coverage is measured over the 100 largest buyers by volume, and funder lookups for launches that are no longer watched are dropped. A seller's funder is looked up before the sell counts as organic, and the launch is held in the window while that lookup is outstanding; a seller whose funder cannot be read only fails the `buyers` signal, it does not release the launch `DEAD`.
- **Feed gaps.** When the pump log stream may have missed logs (the websocket closed, no slot heartbeat for 10 s, a slot jump, an RPC switch, or a log subscription that delivers nothing for 15 s), the feed shows `RECONNECTING` and every launch in the watch window is released `DEAD` with `FEED_GAP`, because a creator sell in the gap would never arrive. The status goes back to `ACTIVE` when the socket reopens or a slot arrives in order (after a slot jump, the slot after the jump); a gap opened by an RPC switch also ends on the first log from the new subscription. The feed telemetry counts the gaps (`feedGaps`, `lastFeedGap`). **Delivery watchdog:** the feed is `ACTIVE` only once the server has confirmed the log subscription. If neither a log nor a slot arrives for 15 s (`FEED_NO_DELIVERY_MS`) while the subscription was never confirmed, or the slot subscription was (so the silence means a deaf socket, not a quiet cluster), a `NO_DELIVERY` gap opens and the subscription moves to a fresh websocket to the same endpoint. Each try that delivers nothing doubles the wait, up to 300 s, and from the third try the status is `ERROR` until a log or slot arrives. Exits and position marks read over HTTP, so a deaf socket cannot hold an exit. A switch of the RPC endpoint moves the log subscription and the creator lookups to the new endpoint. Launches quoted in a mint other than SOL are not watched (`nonSolQuoteSkipped`).
- **No mainnet HTTP feeds off mainnet.** The pump.fun and DexScreener HTTP pollers start only on a read-only server watching a `mainnet-beta` cluster value; on devnet and localnet the feed is the program log stream alone. While the log stream is live the HTTP poll still runs every 10 s (5 s otherwise): the stream only adds new launches, and the curve %, market cap, price and multiple of the listed callouts come from the poll. Each callout card shows how old its snapshot is (STALE past 15 s), and the callout auto-snipe check skips a callout whose snapshot is older than 15 s.
- Kill switch: session budgets (defaults for DEVNET_LIVE: 5 buys, 0.02 SOL incl. fees, 15% loss, 4h; a PAPER session gets 50 buys and spend up to 10 times the paper bankroll; the operator can edit buys and spend, not the loss or time limit; a DEVNET_LIVE session's spend and buys are saved and carry over a mode change, a kill and a restart until 4 h after the session started, so setting the mode again never hands out a fresh real-SOL budget, and a session that has used it is refused with `SESSION_BUDGET_USED`), negative expectancy over the last 20 verified closed trades, 8 losses in a row, 2 slippage breaches, readiness red over 10s, and low wallet drop to SHADOW; an unexplained wallet balance fall (DEVNET_LIVE wallet audit; SOL arriving is only logged) halts every buy plus the take-profit and stale exits and sets auto OFF, while stop-loss, trailing stop, manual close and panic still run. Emergency procedures: [`docs/RUNBOOK.md`](docs/RUNBOOK.md).
- Thresholds (holder concentration 20% top-10 / 5% creator, kill-switch limits, watch-window numbers) are conservative overnight defaults, **not validated on real launches**.
- **The holder gate counts the creator's funder cluster.** At the buy (PAPER and LIVE) the owner of each of the 20 largest token accounts is read (up to 4 extra RPC reads of 5 accounts each: QuickNode's entry plan refuses more than 5 per call) and looked up in what the watch window's funder lookups learned: a holder the creator funded, directly or through one wallet, counts in the 5% creator share (for the second hop the watch window also looks up the funder of each looked-up wallet's SOL sources, up to 50 per launch); a holder whose owner or funding is unknown, whose history was not read in full, or one of whose sources was never looked up, is never taken as independent: all such holders together count as one holder in the 20% top-10 share, and their holdings also count in the 5% creator share, since any of them may be the creator's. The RPC lists at most the 20 largest token accounts, so the supply outside them is unseen and counts the same way as an unknown holder (in both shares): a launch whose holders past the 20th account hold more than 5% between them is refused, and a token supply that cannot be read refuses the buy. A coin whose buyers were never looked up (a manual buy of a launch the window did not watch) therefore needs its 20 largest outside holders, summed, under 5%.

## 👁️ Read-only mode

`APEX_READ_ONLY=true` makes the server watch a cluster and paper trade against what it sees; it cannot sign or send anything. Startup refuses if any signing key is configured (`OPERATOR_PRIVATE_KEY`, `SOLANA_PRIVATE_KEY`, `SIGNER_KEYPAIR_PATH`, or a default `.apex_trading_keypair.json`) or if `ALLOW_LIVE_REAL_MONEY_TRADING=true`. While on: the signer loads no key and cannot generate or import one, every transport throws before touching the network, arming LIVE returns HTTP 409, and auto allows only OFF, SHADOW and PAPER. The threshold and order-size editors still work, because they change what is bought, not whether anything can be sent. Code: `server/solana/readOnly.ts`. A read-only server is allowed to watch mainnet (that is what accepting a `mainnet-beta` cluster value is for), because it can never sign or send on any cluster. Trading, paper or live, against real funds is still never done here: trading stays on devnet or localnet.

## 📼 Recording and replay backtest

The launch recorder saves every launch the watch window scores while the app runs against a pump.fun feed. `GET /api/backtest/recording` reports what is stored. `GET /api/backtest/replay` replays the auto trader's own rules over those recorded launches: the real watch window (same 20 s and 120 s timing), the real confluence engine and the real exit engine polled every 3 s, with fills, latency and costs from the same model the offline studies use (`server/backtest/costModel.ts`): the buy lands 1.5 s after the release and each sell 1.5 s after its decision, at the curve state then (both assumptions until the devnet latency measurement replaces them), the pump.fun fee (1.25% by default) is charged on the buy and on every sell, and every transaction sent pays the network fee, the priority fee and a 0.0001 SOL tip. Closed (realized) results and positions still open at the end are reported apart, and a headline over every entry adds the open ones marked at the last price. Each launch says how its recording ended (the whole window, cut by the trade cap, a restart or a feed gap, graduated, or unresolved with no END row) and the summary gives each group apart. A launch is taken as recorded only up to its END row, or its last recorded row when it has none, and no buy is entered that would land after that; the recorder writes a marker row when it starts and on every feed gap, and a launch whose recording spans one is cut there (DEAD when the gap came before the watch verdict, as live). The report lists what it does not replay by the direction each gap moves the result. `?minScore=N` replays at another threshold without changing the live one. It covers the newest 5,000 launches by default (`APEX_REPLAY_MAX_LAUNCHES`), and the response says how many were replayed.

At the buy it applies what `executeSnipe` checks: the dev-holding limit in force (`maxDevHoldingPct`, default 5%, from the recorded trades) and the confluence score taken again against the threshold. The replay does **not** include the mint and freeze authority checks, the coordinator's eligibility filter (its holder figures come from an RPC holder read), risk limits and capital sizing, or failed transactions, so its result is optimistic by that much. The recorder saves each launch's live creator report, and the replay scores the creator with it from the moment it landed; launches recorded without one (the public corpus, recordings made before this) score 0 of its 5 points, as live does without a report, where live can add up to 5 for an established wallet. With nothing recorded, there is no result. Recorder limits are in `server/backtest/recorderConfig.ts`; the oldest launches are dropped once the row or age limit is reached. Code: `server/backtest/`.

A `POSITION_MARK_UNAVAILABLE` clears when its position closes. If the list cannot be read the stack says so. Alerts live in memory; a restart forgets them (the journal keeps the events).
