# Latency: stages and time limits

What the trade path does between a launch on the feed and a landed buy or sell, and every time limit in the code that delays or refuses an order. It describes the integration snapshot 3f890ed (the 767c13a limits plus the feed delivery watchdog and the disk warning; the constants are checked against the code by `tests/s3j_docs_constants.test.ts`). **Devnet and localnet only.**

The name "HFT" is historical. Auto buys 20 to 120 s after a launch's first trade (the watch window), not at block 0; exits are polled every 3 s; and every RPC call goes over one shared connection. Nothing here claims a latency advantage. See [`KNOWN_RISKS.md`](../KNOWN_RISKS.md) section 8 for what the scores can reach.

`tests/s3j_docs_constants.test.ts` reads the constants named in the table of limits from the source and fails if one no longer has the value stated here. Each reference in the Code columns names a file and a piece of code in it (search the file for that text); the test fails if the text is gone. There are no line numbers because every patch moves them.

The exit delay stays an assumption until a devnet sell-latency measurement replaces it. They are not live latencies: the live path has no fixed delay, only the limits in section 3 |
| The number of RPC round trips per stage | the HFT pipeline draft (not in this repository), written at commit 9b9f568 | **Not re-counted at this snapshot** (the readiness gate, request timeouts and blockhash-expiry watch were added since). Do not use it for a decision |

To measure a stage yourself: run with `APEX_TRACING=true` (spans `watch.release`, `snipe.execute`, `gate.confluence`, `trade.execute`, `gate.eligibility`, `risk.evaluateOrder`, `tx.build`, `guard.blockhash`, `tx.sign`, `guard.sendCluster`, `guard.genesis`, `tx.submit`, `tx.confirm`, `tx.reconcile`, `exit.close`, one `POST` span per RPC call; see [`TRACING.md`](TRACING.md)). `GET /api/system/latency` reports measured send-to-confirm per transport, mode and side. `APEX_TRACING=true npm run devnet:e2e` shows the spans of a real devnet round trip; that check has not been run for this document.

## 2. Stages

| # | Stage | What bounds it | Code |
|---|---|---|---|
| 1 | Detection: pump program logs and slot notifications over the websocket, decoded into Create and Trade events | Push. A websocket drop, 10 s of slot silence, a slot jump or an RPC switch opens a gap and releases every watched launch `DEAD` | `server/solana/pumpFeedListener.ts` (`this.connection.onLogs(`) |
| 2 | Watch window: real trades for 20 to 120 s from the first trade; HOT early, READY at the end, DEAD on a creator sell, no trades or a curve past the cap; held while a seller's funder lookup is outstanding | The main delay, by design | `server/signals/watchWindow.ts` (`public evaluate(`) |
| 3 | Release to auto candidate: gates, one candidate in flight, a queued release retried after 2 s while it is younger than 6 s | Queue age is measured from the release, not from when it was queued | `server/auto/controller.ts` (`public submitCandidate(`) |
| 4 | `executeSnipe`: price, sizing, pool, freeze authority, creator share, confluence score | Manual routes join here | `server/memecoinAggregator.ts` (`public async executeSnipe(`) |
| 5 | `executeTrade` LIVE branch up to the reservation: armed, cluster, per-buy readiness, curve read, eligibility, sizing, quote, risk engine, duplicate checks | Several sequential RPC reads; the curve read starts the 5 s market-data clock | `server/execution/coordinator.ts` (`private async executeTradeUntraced(`) |
| 6 | Snapshot, build, optional blockhash check, signature, Q17 re-check, `orders` row | The per-buy readiness gate runs again here | `server/execution/coordinator.ts` (`TradeReconciler.capturePreTradeSnapshot(`) |
| 7 | `submitAndConfirmWithRetry`: read-only check, send-cluster check, cached genesis check, then the PENDING row | A refusal here leaves no row | `server/execution/coordinator.ts` (`public async submitAndConfirmWithRetry(`) |
| 8 | `submitAndConfirmInner`: the guards again, then send and the confirm watch | 15 s watch plus up to 60 s while the blockhash is valid | `server/execution/coordinator.ts` (`private async submitAndConfirmInner(`) |
| 9 | Reconcile the fill and save the position | The position, and so its stop-loss, exists only after the fill is reconciled | `server/execution/reconciliation.ts` (`public static async reconcileBuyTransaction(`) |
| 10 | Exit pass: every 3 s, marks read, rules evaluated, sells started together and awaited up to 2.5 s | A sell blocks only its own position | `server/execution/coordinator.ts` (`public evaluateAndProcessExits(`) |
| 11 | LIVE sell: cluster check, venue, quote, build, snapshot, optional blockhash check, signature, simulation, submit | Not gated by readiness | `server/execution/coordinator.ts` (`public closePosition(`) |

The order of the guards between stages 5 and 8 is drawn in diagram 3 of [`ARCHITECTURE.md`](ARCHITECTURE.md), and `tests/s3j_docs_constants.test.ts` checks the diagram's edge order against the first calls in `executeTradeUntraced` and `submitAndConfirmWithRetry`.

## 3. Time limits

Each row: the limit, its value, what happens on a breach, and where it lives at 3f890ed.

| Feed slot silence | 10 s without a slot notification (`FEED_SLOT_SILENCE_MS`) | Gap: status `RECONNECTING`; every launch in the window released `DEAD` `FEED_GAP` | `server/solana/pumpFeedListener.ts` (`FEED_SLOT_SILENCE_MS =`) |

## 4. Known gaps in the limits

- The failed-sell retry wait and the 6 s rate-limit wait also run down on the monotonic clock (A3), so a wall clock set back no longer holds a position's exits past the wait. Before A3 they could be held until the old deadline; the regression tests are in `tests/s271_clock_back_exits.test.ts`.
- `WALLET_UNKNOWN` waits for `READINESS_RED_LIMIT_MS` (10 s) of no good balance read since 3E; before 3E it fired on the first null read.
- The independent blockhash check (`APEX_VERIFY_BLOCKHASH`) asks through a plain web3.js connection, so it has no per-call timeout and web3.js sleeps on an HTTP 429. That is from the audit; it was not re-measured here.
- The one-position cap of DEVNET_LIVE and the open-position count read ACTIVE rows of every mode; 3B is planned to change what counts (`ARCHITECTURE.md` section 2).
